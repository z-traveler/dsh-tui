# 下游开发流程

本页说明私有下游的完整开发流程：从新需求开发、整理提交合入 `z` 分支，到跟进上游同步。补丁规范、分支命名与上游同步的通用约定见工作区 `../AGENTS.md`；打包、安装与回退步骤见[发布流程](release.md)。

## 分支与提交

- `main` 分支只镜像上游，`z` 是下游稳定分支，发布标签只打在 `z` 上。主工作目录 `dsh-tui/` 固定停在 `z` 分支，只用来查看代码和核对发布，不要直接在里面开发或保留未提交的改动。
- `z` 分支是在上游稳定标签之上叠加的一串功能提交，每个功能对应一个独立提交，提交信息使用 conventional 前缀。功能清单见 [README.md](README.md)。
- 开发新需求时，从最新的 `z` 切出 `feature/<功能>` 分支，并在工作区 `.worktree/dsh-tui/<功能>/` 下创建对应的工作树。同一需求自始至终只用这一个分支，不要再基于它串联新建其他分支。
- 合入 `z` 之前先整理好提交历史：修改已有功能时，用 `git commit --fixup` 加 `rebase --autosquash` 把改动并回 `z` 上对应的功能提交；新功能则整理为单个独立提交。整理完成后 rebase 到最新 `z`，再通过 fast-forward 合入（`z` 不产生 merge 提交）。改写过 `z` 的历史后，推送必须使用 `--force-with-lease`。
- 如果 `z` 顶端已经打过发布标签，后续改动直接以新提交追加到顶端，不要改写已发布的历史，以免标签脱离 `z`。这些追加提交等下次跟进上游 rebase 时再并入各自对应的功能提交。
- 交付完成后，清理对应的工作树和已经合入的分支。

## 需求与记录

- `.scratch/` 是不纳入版本库的本地工作区，用来存放规格、工单、交付记录与验收产出（格式见 [issue-tracker.md](../agents/issue-tracker.md)）。其中的内容不作为长期依据。
- 需要长期保留的信息在合入前写进仓库：功能说明、接口契约与验证命令写入 `docs/downstream/<功能>.md` 并更新 [README.md](README.md) 的功能表；跨任务有效的架构与设计决策写进 `docs/adr/`；领域术语写进根目录 `GLOSSARY.md`。可复用的演示配置放在 `scripts/downstream/fixtures/`。
- 下游文档只使用中文，不要出现本机绝对路径、工作树路径、提交 SHA、CI run 编号或一次性的验收过程记录。
- 上游 README、`AGENTS.md` 上游部分、`docs/` 与 `guide/` 下的上游手册不写下游功能；上游贡献指南中“同步 README 与用户手册”的要求不适用于下游功能。

## 实现

- 业务插件所需的 TUI 能力（如卡片、输入补全、浮窗、会话接口以及外部集成扩展口）都在本仓库以通用接口实现，具体业务规则、数据和计算留在业务插件中。
- 新逻辑放进独立模块，上游文件里只加调用点和配置声明；不要复制上游组件来改。
- 新增的外观与布局默认保持上游行为，通过配置开启。卡片类改动必须同时适配 `legacy` 与 `pi-like` 两种卡片样式。
- 代码、注释、标识符与测试名称中不要提及 Pi 等外部参照；参照来源只写在文档里。
- 读取未在 `inject` 中声明的可选 Cordis 服务时，必须用 `ctx.get('<服务>')` 探测。直接访问 `ctx.<服务>` 会在该服务已注册时抛错并导致启动失败。测试必须覆盖「服务已注册、但调用方插件未声明注入」的情形。

## 验证与验收

1. **定向验证**：日常只运行与改动相关的 `scripts/downstream/verify-*` 和上游聚焦脚本，并配合必要的编译，不必每次都跑全量。改动 `channel/`、`dsh-adapter/` 等共享路径时，需要加跑包含它们的 CI 回归分组（`node scripts/run-ci-group.mjs <组> --shard <n>/<总数>`）：上游单元测试常使用精简的假宿主调用这些路径，局部定向脚本往往覆盖不到。
2. **可见效果**：终端可见的改动使用 `scripts/downstream/*-demo.tsx` 中的固定演示场景核对效果。演示默认使用 `pi-like` 卡片样式和中文内容，覆盖多实例、状态更新、失败场景、窄屏，以及 inline 与 fullscreen 两种模式。如果演示表现与真实运行不一致，先排查是演示脚本的问题还是实现的问题。
3. **真实环境**：当用户要求在真实环境中验收时，运行 `node scripts/downstream/run-local-dst.mjs`。脚本会编译当前代码，临时挂载到正式的 `dsh-tui` profile 并沿用其凭据与会话，退出时自动恢复原包。运行期间不要再用同一个 profile 启动其他 TUI 实例。
4. **交付入口**：交给用户验收的命令，先由 agent 原样执行一遍，确认启动无报错、功能正常可见，并向用户说明操作步骤和需要观察的内容。
5. **收尾**：用户验收通过后只修复阻塞问题，整理好提交并合入 `z`，再按发布流程打包。发布 CI 会运行全量门禁。

## 跟进上游

1. 从 `z` 创建候选分支与工作树，执行 `git rebase --onto <上游稳定标签> <当前基线标签>`。冲突主要集中在 [README.md](README.md) 列出的上游接入点；解决冲突时要同时保留上游和下游的意图，已经被上游原生实现的下游改动可以直接删除。
2. 使用 `git range-diff` 逐个核对新旧功能提交。
3. 完成编译和 typecheck，运行全部 `scripts/downstream/verify-*` 以及各功能文档「验证」一节列出的脚本（部分下游回归脚本位于 `scripts/`，例如 `verify-input-completions.tsx`），再运行冲突文件相关的上游脚本；如果共享渲染或 `Chat` 发生冲突，补跑上游 CI 回归。
4. 验证通过后推进 `z` 分支，同时把 `main` fast-forward 到对应上游位置并推送。

获取上游标签请使用 `git fetch upstream --tags`。本仓库启用了 `fetch.prune`，如果对 `origin` 使用显式标签 refspec 拉取，会误删本地的上游 `v*` 标签。

初次检出仓库时，依次执行 `git submodule update --init --recursive`、`pnpm install --frozen-lockfile --ignore-scripts` 与 `pnpm compile`。
